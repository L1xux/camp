# CAMP (Campaign & Marketing Platform) 기획

패션 기업의 인플루언서·PPL 마케팅 운영 시스템 + 대화형 동적 대시보드.
F&F Java/Spring 백엔드(ERP/AI시스템) 직무를 겨냥한 포트폴리오 프로젝트.

## 1. 문제 정의

- **누가**: 패션 브랜드(MLB·디스커버리류)의 마케팅 담당자·팀장·본부장
- **어떤 불편**: 인플루언서 섭외~계약~집행~성과 확인이 엑셀·메신저·수기로 흩어져 있다.
  성과 질문("작년 F/W 캡 카테고리에서 누가 잘했지?")의 답을 얻으려면 담당자가 자료를 뒤져야 한다.
- **지금은 어떻게**: 엑셀 대장 + 대행사 리포트 + 수기 결재
- **왜 불충분한가**: 브랜드별 권한·결재 이력·예산 통제가 시스템으로 강제되지 않고,
  성과 데이터가 축적·질의 가능한 형태로 남지 않는다.

근거: F&F는 인플루언서·PPL 관리 마케팅시스템을 실제 운영 중이며(전자신문 2022-11),
Snowflake 사례에서 "RAG 기반 동적 대시보드"를 다음 목표로 공표했다. 이 프로젝트는
그 현재(운영 시스템)와 미래(대화형 대시보드)를 함께 구현한다.

## 2. 핵심 사용자 시나리오

1. 마케터가 2027 S/S 캠페인을 만들어 인플루언서 후보를 담고, 계약을 올리면
   금액 구간에 따라 결재선이 자동 결정되어 승인 후 계약이 유효화된다.
2. 매일 새벽 배치가 집행 콘텐츠의 성과를 수집(유튜브 실API/시뮬레이터)해
   일별 스냅샷으로 쌓고, 캠페인 대시보드가 갱신된다.
3. 본부장이 자연어로 "이번 시즌 MLB 캠페인 ROI 상위 5명은?"을 물으면
   AI가 MCP 도구(Text-to-SQL+Validator, 문서 RAG)를 호출해 차트와 근거를
   스트리밍으로 그려준다. 같은 질문을 Claude Desktop에서 해도 동일하게 동작한다.

## 3. 성공 기준

실사용자 없는 포트폴리오 프로젝트 — 품질 목표(6)와 아래 기준이 그 역할을 한다.

- 면접 데모: 역할 전환 포함 전체 한 바퀴(캠페인 생성→결재→배치→AI 질의)가 5분 내 재현
- 골든셋 평가가 CI에서 회귀 게이트로 동작하는 것을 레포 이력으로 증명

## 4. 범위

### MVP (상세 목록은 GitHub Projects 보드)

1. **인플루언서 풀** — 등록·검색·프로필, 채널 1:N(인스타/유튜브)
2. **캠페인** — 브랜드·시즌·예산·기간, 상태머신(기획→섭외중→집행중→종료→결산완료), 후보 담기·확정
3. **계약·결재** — 금액 구간별 다단계 결재선(ApprovalStep), 승인/반려/재상신, 예산 초과 통제
4. **성과 수집 배치** — MetricsCollector 포트 + 어댑터 2개(YouTube 실API / 시뮬레이터), 일별 스냅샷, 집계
5. **MCP 도구 계층** — 비즈니스 기능·데이터 질의를 MCP 서버로 노출, Validator(권한·화이트리스트·비용) 내장
6. **대화형 동적 대시보드** — MCP 도구를 소비하는 스트리밍 AI UI(React+SSE), 질의→차트 동적 생성
7. **평가·관측 하네스** — 골든셋 평가 + CI 게이트, 구조화 로깅(request_id 전 구간),
   LLM 관측(토큰·비용·지연), Sentry, METRICS.md 지표 운영

### Non-goals (의도적으로 안 하는 것)

- **인스타그램 실API 연동** — 인플루언서 본인의 OAuth 동의가 필요해 개인이 불가.
  포트로 격리하고 시뮬레이터 어댑터로 대체(전환 = 어댑터 교체)
- **정산·지급/회계 연동** — 범위 폭발. 계약 금액 관리까지만
- **인플루언서 본인용 외부 포털** — 외부 사용자 등장 시 인증 체계 2배
- **다국어·해외법인** — 단일 조직 가정
- **GraphRAG** — 관계가 이미 RDB에 정형화되어 있어 SQL 조인이 그래프 탐색을 대체.
  비정형 문서만 하이브리드 RAG로 (ADR 예정)
- **AI 인플루언서 적합도 판정** — 대시보드가 이미 LLM·RAG·스트리밍을 증명, 신뢰성 논란 대비 실익 없음

## 5. 데이터

- **정형(시드)**: 인플루언서 수천 명 × 채널, 캠페인 수백 건, 3년치 일별 MetricSnapshot
  수백만 행 — 파티셔닝·인덱스·실행계획 튜닝의 재료. 시드 생성 스크립트로 재현 가능하게
- **실데이터**: 유튜브 공개 통계(Data API, 키만으로 가능) — 실존 채널 소수 등록해 실연동 증명
- **비정형(시드)**: 브랜드 가이드라인 2부, 표준·개별 계약 조항, 시즌별 캠페인 결산 보고서 10여 부
- **민감도**: 전부 가상 인물·가상 계약. 실존 유튜브 채널은 공개 통계만 저장

## 7. 아키텍처 개요

### 7.1 컴포넌트 구성 — Gradle 멀티모듈 단일 배포

```
domain/        # 순수 Java — 상태머신·결재 규칙·예산 불변식 (Spring 의존 0, 테스트 최다)
application/   # 유스케이스, 포트 정의 (MetricsCollector, DocumentStore, …)
adapter-web/   # REST API + SSE (React 소비)
adapter-mcp/   # Spring AI MCP Server — 웹과 동일 유스케이스 공유
adapter-batch/ # 성과 수집 스케줄러 (수동 트리거 지원)
infra/         # JPA·Oracle(23ai Vector 포함)·LLM·YouTube 클라이언트 구현체
```

의존 방향은 빌드로 강제(domain은 Spring을 import 불가). 스택:
Java 21 + Spring Boot 3.x + Spring AI / Oracle Database Free 23ai(Docker) /
React + TypeScript + Vite / LLM: OpenAI API(인터페이스로 격리, 교체 가능).

### 7.2 데이터 흐름

- **운영**: React → REST → 유스케이스 → 도메인 규칙 → Oracle
  (예: 계약 등록 → 결재선 자동 결정 → 승인 완료 시 유효화)
- **배치**: 스케줄러 → MetricsCollector 포트 → (YouTube 실API | 시뮬레이터) →
  스냅샷 벌크 적재 → 집계 갱신. 건별 실패는 스킵+기록
- **AI**: 질문 → LLM 라우팅 → MCP 도구 선택
  ├ query_metrics: Text-to-SQL + Validator(브랜드 권한 WHERE 강제 주입·화이트리스트·비용)
  └ search_documents: 하이브리드 RAG(Oracle 23ai 벡터 + 키워드, brand_id 필터)
  → 결과 합성(수치+문서 근거, 출처 구분) → SSE 스트리밍 → 차트 렌더.
  웹 챗과 Claude Desktop이 같은 도구·같은 Validator를 통과

### 7.3 주요 인터페이스 초안

- `POST /api/contracts` → 결재선 포함 계약 생성: `{campaignId, influencerId, amount}` →
  `{contractId, status: PENDING_APPROVAL, approvalLine: [...]}`
- `POST /api/assistant/query` (SSE) → `{question, conversationId}` →
  스트림: `tool_call → tool_result → chart_spec → answer_delta*`
- MCP: `search_influencers`, `query_campaign_metrics`, `search_documents`,
  `get_campaign_summary`, `list_pending_approvals`

## 8. 운영 정책

- LLM·외부 호출: 타임아웃 필수, 지수 백오프 재시도 ≤ 2회, 최종 실패 시 정직한 실패 응답
- Validator 차단 시 사유를 사용자에게 그대로 노출
- LLM 비용 상한: 일 $2 초과 시 AI 질의 기능 차단(운영 화면은 정상 동작)
