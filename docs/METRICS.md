# CAMP 운영 지표

`docs/PLAN.md` 6절 품질 목표를 측정 가능한 형태로 옮긴 문서다.
목표를 벗어나면 원인 분석 이슈를 만드는 것이 규칙이다.

기능이 붙을 때마다 이 문서를 보강한다. 지금은 수집 수단이 없는 지표가 대부분이므로,
정의와 목표를 먼저 고정해두고 수집이 붙는 이슈에서 수집 방법 칸을 채운다.

| 지표 | 정의 | 수집 방법 | 목표 | 확인 주기 |

LLM 일일 비용은 PLAN 6절이 아니라 8절 운영 정책에서 왔다. 코드가 이미 상한을 강제하고
있어 측정 대상이므로 함께 둔다.

## 골든셋 지표

앞의 세 지표는 골든셋을 돌려서 나온다. 골든셋은 대표 질문과 기대 결과를 짝지어 파일로
고정해둔 평가용 데이터이며 `eval/golden.jsonl` 에 10~15건으로 시작한다. 케이스 하나에
질문, 호출자의 브랜드와 역할, 기대 도구, 기대 SQL 구조, 기대 답변 요건이 들어간다.

케이스 예시다.

- 질문: 이번 시즌 A브랜드 캠페인 ROI 상위 5명은?
- 호출자: A브랜드 마케터
- 기대 도구: `query_campaign_metrics`
- 기대 SQL 구조: `metric_snapshot` 참조, `brand_id = A` 조건 포함, ROI 내림차순 5건
- 기대 답변 요건: 인플루언서 5명과 수치 포함

**도구 선택 정확도**는 LLM 이 기대한 도구를 실제로 호출한 비율이다. 문서를 찾아야 할
질문에 SQL 도구를 부르면 실패다.

**SQL 구조 정확도**는 실행된 SQL 이 기대 구조를 충족한 비율이다. 문자열 일치가 아니라
참조 테이블과 핵심 조건이 맞는지를 본다. 같은 질의를 쓰는 방법이 여러 가지라 완전
일치로 판정하면 멀쩡한 SQL 도 실패로 잡힌다.

**권한 우회 차단률**은 권한 침해 케이스 중 Validator 가 막아낸 비율이다. A브랜드
마케터가 B브랜드 실적을 묻는 식의 공격 케이스를 넣어두고, 한 건이라도 뚫리면 다른
지표와 무관하게 CI 를 실패시킨다.

LLM 출력은 같은 입력에도 매번 달라져서 단위 테스트로 검증할 수 없다. 대신 프롬프트를
고치거나 모델을 바꿀 때마다 골든셋 전체를 다시 돌려 점수가 기준선 아래로 떨어지면 머지를
막는다. 평가가 회귀 테스트 역할을 하는 것이다. 채점은 실행된 도구명 대조, SQL 의 AST
검사, 응답 문자열 요건처럼 결정적 규칙으로 한다. LLM 으로 LLM 을 채점하면 채점기 자체를
또 검증해야 해서 이 규모에서는 쓰지 않는다.

기대값을 고정할 수 있는 근거는 시드 데이터가 결정적이라는 점이다. #42 가 만드는 시드가
고정이므로 ROI 1위의 정답이 실행마다 같다.

## 임계를 벗어나면

1. 골든셋 지표 세 개는 CI 게이트다. 미달하면 머지가 막힌다.
2. 나머지는 주간 관측 리뷰에서 확인하고, 벗어난 지표마다 원인 분석 이슈를 만든다.
3. 배포 직후 지표가 나빠졌으면 직전 태그 재배포가 기본값이다. 원인 분석은 롤백 뒤에 한다.
