# ADR-004: LLM 트레이싱은 Spring AI Observability 로 계측하고 Langfuse 로 수집한다

- 상태: **채택** (2026-08-06) — 반론 세션은 UiJin 결정으로 생략, 초안을 직접 승인
- 상황: 모든 LLM 호출의 입력, 출력, 토큰, 비용, 지연을 trace 로 남기고 retrieval 을
  하위 span 으로 분리해야 한다 (#34). request_id 를 trace 속성으로 첨부해 로그,
  Sentry 와 상호 추적한다. 후보는 Langfuse Java SDK 직접 계측,
  Spring AI Observability 계측 + Langfuse OTLP 수집,
  Spring AI Observability 계측 + 범용 APM.

## 확인한 사실 (2026-08-06)

| 항목 | 확인 내용 |
|---|---|
| Langfuse Java SDK | 존재하지만 메인테이너가 트레이싱 용도로 비권장. "the OpenTelemetry integration is significantly better in terms of performance and out-of-the-box functionality" — https://github.com/orgs/langfuse/discussions/4589 |
| Langfuse OTLP 수집 | OTLP/HTTP 엔드포인트 제공. 인증은 public key 와 secret key 의 Basic Auth — https://langfuse.com/integrations/frameworks/spring-ai |
| Spring AI 계측 | ChatModel 과 VectorStore 호출을 Micrometer Observation 으로 계측한다. Micrometer Tracing 과 OpenTelemetry 브리지로 OTLP 전송 |
| 내용 캡처 제약 | 커스텀 ObservationFilter 없이는 생성 span 의 입력과 출력이 Langfuse 에서 null 로 보인다. 위 연동 가이드에 명시 |
| Langfuse 셀프호스트 | v3 는 ClickHouse, Redis, Postgres, S3 를 요구한다 |

## 결정

계측은 Spring AI 내장 Observability 를 쓴다. Micrometer Observation 이
OpenTelemetry 브리지를 거쳐 Langfuse 의 OTLP 엔드포인트로 전송된다.
백엔드는 Langfuse Cloud 무료 티어.

## 이유

1. Langfuse 메인테이너가 Java 트레이싱에 자사 SDK 대신 OpenTelemetry 를 권장한다.
   성능과 기본 기능에서 낫다고 공식 토론에서 밝혔다.
2. Spring AI 가 ChatModel 과 VectorStore 호출을 이미 계측하므로 retrieval 하위 span
   분리가 추가 코드 없이 나온다.
3. Langfuse 는 토큰, 비용, 프롬프트를 LLM 전용 화면으로 보여준다. 범용 APM 에는
   이 화면이 없어 METRICS.md 의 질의당 비용 지표를 운영할 수 없다.

## 버린 대안

**Langfuse Java SDK** — 메인테이너가 트레이싱 용도로 비권장. 프롬프트 관리 용도에만 적합하다.

**범용 APM (Jaeger, Tempo 등)** — 수집과 저장은 되지만 LLM 비용과 프롬프트 화면이 없다.
비용 지표를 별도로 만들어야 해 도입 실익이 없다.

**Langfuse 셀프호스트** — 요구 인프라 4종을 로컬 PC 에서 상시 구동하는 부담이 크다.
docker-compose 스택이 Oracle 하나인 현재 구성을 유지한다.

## 트레이드오프

- 프롬프트와 응답이 외부 클라우드에 저장된다. 이 프로젝트 데이터는 전부 가상이라 수용한다.
- 생성 span 의 입력과 출력을 보려면 Langfuse 문서가 안내하는 커스텀 ObservationFilter 를
  붙여야 한다. 트레이싱 구현 범위에 포함한다.
- 외부 SaaS 의존이 생긴다. Langfuse 장애 시에도 LLM 호출은 정상 진행되어야 하며,
  이 예외 케이스는 #34 에 이미 있다.
