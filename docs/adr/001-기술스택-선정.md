# ADR-001: 기술스택 선정

- 상태: **제안** (2026-08-01) — 반론 세션 대기. 반론을 버틴 항목만 '채택'으로 승격하고,
  반론 내용으로 각 항목의 '기각 근거' 칸을 보강한다.
- 결정 범위: 백엔드 언어·프레임워크 / AI 계층 / DB / 모듈 구조 / 프론트 / LLM 프로바이더
- 전제: 결재·권한·배치가 있는 사내 비즈니스 시스템 + LLM 질의 계층. 1인 개발, 5일 스프린트,
  로컬 Docker 기반 실행 환경.

---

## 결정 1. 백엔드 언어·프레임워크

**옵션**: Java 21 + Spring Boot 3.x / Kotlin + Spring Boot / Node.js(NestJS) / Python(FastAPI)

**선택**: Java 21 + Spring Boot 3.x

**이유**:
1. 이 시스템의 중심 문제는 트랜잭션 경계다 — 결재 승인과 계약 유효화, 예산 차감이 한 단위로
   묶여야 한다. Spring의 선언적 트랜잭션·영속성 생태계(JPA)가 이 문제를 가장 오래, 가장 넓게
   검증해온 조합이다.
2. 배치가 1급 요구사항인데(일별 수집·마감), 스케줄링·청크 처리·재시도를 갖춘 Spring Batch
   생태계가 있어 직접 만들 것이 적다.
3. Java 21의 record(불변 도메인 값), sealed interface(상태머신 상태의 컴파일타임 봉인),
   virtual thread(외부 API 동시 수집)가 이 프로젝트의 요구와 직접 맞물린다.
4. Oracle과의 궁합 — JDBC·드라이버·문서 축적이 가장 두텅다.

**트레이드오프**: Kotlin 대비 보일러플레이트 증가(record로 완화), FastAPI 대비 초기 셋업 무거움.

## 결정 2. AI 계층

**옵션**: Spring AI(백엔드 단일 스택) / Node AI 게이트웨이 분리(Vercel AI SDK) / HTTP 직접 호출 수제 구현

**선택**: Spring AI

**이유**:
1. AI 도구의 실행 지점이 도메인 바로 옆이어야 한다 — `query_campaign_metrics`는 브랜드 권한
   검증(Validator)을 거쳐야 하는데, 이 규칙은 백엔드 도메인에 있다. AI 계층을 별도 서비스로
   빼면 권한 로직이 두 곳으로 갈라지거나 네트워크 한 번을 더 탄다.
2. 도구를 한 번 정의해 웹 SSE 챗과 MCP 서버 양쪽에 재사용할 수 있다(Spring AI가 MCP
   서버/클라이언트 공식 지원). 게이트웨이 분리안은 같은 도구를 두 런타임에 이중 정의하게 된다.
3. 운영 대상 프로세스가 1개로 유지된다 — 1인 5일 개발에서 배포·관측 포인트 증가는 실질 비용.
4. 수제 구현은 MCP 프로토콜·스트리밍 재작성에 공수가 소모되고, 그 코드가 프로젝트의 증명
   대상도 아니다.

**트레이드오프**: Spring AI는 신생이라 API 변동 리스크 — 버전 고정 + 낯선 API 문서 대조를 규율로.
프론트에서 Vercel AI SDK의 UI 훅(useChat)은 차용 가능(스트림 소비 측이므로 백엔드 선택과 독립).

## 결정 3. DB

**옵션**: Oracle Database Free 23ai 단일 / PostgreSQL + pgvector / RDB + 별도 벡터 DB(Qdrant 등)

**선택**: Oracle Database Free 23ai 단일 (정형 + 벡터 + 키워드 검색 전부)

**이유**:
1. 이 시스템의 검색은 하이브리드다 — 계약 조항의 정확 용어("위약금")는 키워드, 서술 질의는
   벡터. Oracle은 Text(키워드)와 AI Vector Search(벡터)를 한 엔진에서 제공해 두 결과를
   SQL 한 방으로 조인·필터(brand_id 격리)할 수 있다. 저장소가 갈라지면 이 필터를 두 번 구현한다.
2. MetricSnapshot 수백만 행의 월 파티셔닝, 실행계획 도구(DBMS_XPLAN)가 기본 제공 —
   대용량 조회 튜닝을 별도 도구 없이 수행·기록할 수 있다.
3. 운영 인프라 1개 — 벡터 DB를 따로 두면 백업·시딩·docker-compose가 전부 이중화된다.
4. Spring AI가 OracleVectorStore를 공식 지원해 통합 비용이 낮다.

**트레이드오프**: pgvector 대비 커뮤니티 자료가 적다. Free 컨테이너 메모리 요구(2GB+)와
이 PC의 IPv4 루프백 이슈 — D1 최우선 검증 항목.

## 결정 4. 모듈 구조

**옵션**: Gradle 멀티모듈 모놀리스 / 단일 모듈 + 패키지 규율(ArchUnit) / 서비스 분리(MSA)

**선택**: Gradle 멀티모듈 모놀리스 — domain / application / adapter-web / adapter-mcp / adapter-batch / infra, 배포 1개

**이유**:
1. 도메인 규칙(결재·예산·상태머신)이 이 시스템의 가장 검증 필요한 부분인데, domain 모듈에
   Spring 의존을 빌드 레벨에서 차단하면 순수 단위 테스트가 강제된다 — 위반이 사후(테스트
   실패)가 아니라 즉시(컴파일 에러) 잡힌다.
2. 인바운드가 3개다(웹·MCP·배치). 모듈 경계가 없으면 어댑터 코드가 유스케이스로 새는 것을
   막을 장치가 리뷰뿐이다.
3. MSA는 이 규모(단일 DB, 단일 팀)에서 분산 트랜잭션·배포 파이프라인 비용만 추가하고
   얻는 게 없다.

**트레이드오프**: 초기 Gradle 설정 비용(반나절 상한). 단일 모듈 대비 파일 이동이 잦다.

## 결정 5. 프론트

**옵션**: React + TypeScript + Vite(SPA) / Next.js / 서버 템플릿(Thymeleaf)

**선택**: React + TypeScript + Vite, 스트리밍은 SSE(fetch 스트림)

**이유**:
1. 인증 뒤의 사내 도구라 SEO·초기 로드 SSR의 이점이 없다 — Next의 서버층은 Spring 백엔드와
   역할이 겹치는 중복 런타임이 된다.
2. 스트리밍 UI·차트 동적 렌더 등 클라이언트 상호작용이 무겁다 — 서버 템플릿으로는 부적합.
3. 개발자가 이미 숙련된 스택(React+Vite)이라 5일 일정에서 학습 비용 0.

**트레이드오프**: 사실상 없음(사내 시스템 전제에서).

## 결정 6. LLM 프로바이더

**옵션**: OpenAI(gpt-4o-mini 계열) / Anthropic Claude / 로컬 LLM(Ollama)

**선택**: OpenAI로 시작, `LlmClient` 인터페이스로 격리해 교체 가능하게

**이유**:
1. 주 워크로드가 도구 호출(Text-to-SQL·검색 라우팅)인데 gpt-4o-mini는 이 용도에 충분한
   품질을 훨씬 낮은 단가로 제공 — 질의당 비용 목표($0.02) 안에 여유 있게 들어온다.
2. 보유 키 재사용으로 발급 절차·추가 비용 0.
3. 프로바이더 우열은 골든셋으로 판정할 문제다 — 인터페이스 격리 + 평가 하네스가 있으므로
   교체 실험이 설정 변경 수준이 된다. 지금 최선을 고르는 것보다 바꿀 수 있는 구조가 중요.
4. 로컬 LLM은 도구 호출 신뢰도가 골든셋 목표(85%)를 위협하고 실행 환경 재현 부담이 크다.

**트레이드오프**: 단일 외부 의존 — 타임아웃·재시도 ≤2·일 비용 상한($2)을 전역 정책으로 방어.
