# ADR-001: 기술스택 선정

- 상태: **제안** (2026-08-01) — 반론 세션 대기. 반론을 버틴 항목만 '채택'으로 승격하고,
  반론 내용으로 각 '버린 대안' 칸을 보강한다.
- 결정 범위: 백엔드 언어·프레임워크 / AI 계층 / DB / 모듈 구조 / 프론트 / LLM 프로바이더

---

## 결정 1. 백엔드: Java 21 + Spring Boot 3.x

- **상황**: F&F 공고가 Java(Spring Boot) 백엔드·Oracle을 명시. 후보: Java/Spring, Kotlin/Spring, Node(NestJS)
- **결정**: Java 21 + Spring Boot 3.x
- **이유**: 공고 스택과의 일치가 이 프로젝트의 존재 이유. Java 21의 record·sealed·virtual thread로
  "낡은 Java"가 아닌 현대적 Java를 증명할 수 있음
- **버린 대안**:
  - Kotlin — 생산성은 높으나 공고가 Java를 명시. "Java로 잘 쓸 수 있는가"가 평가 대상
  - Node/NestJS — 공고의 질문 자체를 비껴감
- **트레이드오프**: Kotlin 대비 보일러플레이트 증가 (record·Lombok 최소 사용으로 완화)

## 결정 2. AI 계층: Spring AI (LLM 호출 + MCP 서버 단일 스택)

- **상황**: LLM API 연동·스트리밍 응답·MCP 노출이 필요. 후보: Spring AI /
  Node AI 게이트웨이 분리(Vercel AI SDK) / HTTP 클라이언트 수제 구현
- **결정**: Spring AI — 도구를 한 번 정의해 웹 SSE 챗과 MCP 서버 양쪽에 재사용
- **이유**: "Java/Spring으로 AI 기능을 만들 수 있는가"가 공고의 핵심 질문.
  게이트웨이 분리는 그 질문을 회피하는 그림이 됨. Spring AI는 MCP 서버/클라이언트를 공식 지원
- **버린 대안**:
  - Node AI 게이트웨이 — AI DX는 최고지만 운영 대상 서비스 +1, 공고 정합성 하락
  - 수제 구현 — 프로토콜 이해 증명은 되나 공수가 MCP SDK 재작성에 소모됨
- **트레이드오프**: Spring AI는 신생이라 API 변동 리스크 — 버전 고정 + 낯선 API 문서 대조를 규율로.
  프론트에서 Vercel AI SDK의 UI 훅(useChat)만 차용해 우대사항도 커버

## 결정 3. DB: Oracle Database Free 23ai (벡터 검색 포함, Docker)

- **상황**: 공고가 Oracle RDBMS를 명시. RAG용 벡터 저장소도 필요.
  후보: Oracle 23ai 단일 / PostgreSQL+pgvector / Oracle + 별도 벡터 DB(Qdrant)
- **결정**: Oracle 23ai 하나로 정형 데이터 + 벡터 + 키워드(Oracle Text) 전부
- **이유**: 공고 정합성 + 인프라 최소화. AI Vector Search로 "Oracle을 벡터 검색까지 쓸 줄 안다"는
  차별화가 생김. Spring AI가 OracleVectorStore 공식 지원
- **버린 대안**:
  - PostgreSQL+pgvector — 생태계·자료 풍부하나 공고의 Oracle 요구와 어긋남
  - 별도 벡터 DB — 관리 인프라 +1, 이 규모에서 하이브리드 검색 이점 없음
- **트레이드오프**: Oracle Free 컨테이너의 리소스 요구량(메모리 2GB+)과
  로컬 구동 리스크(이 PC의 IPv4 루프백 이슈) — D1에 최우선 검증

## 결정 4. 모듈 구조: Gradle 멀티모듈 모놀리스 (헥사고날)

- **상황**: 클린 아키텍처를 어떤 물리 구조로 담을지.
  후보: 멀티모듈 / 단일 모듈+패키지 규율(ArchUnit) / 서비스 분리(MSA)
- **결정**: domain / application / adapter-web / adapter-mcp / adapter-batch / infra 6모듈, 배포는 1개
- **이유**: 의존 방향이 빌드로 강제됨 — domain은 Spring을 import조차 못 함.
  "클린 아키텍처 준수"가 주장이 아니라 컴파일 에러로 증명됨
- **버린 대안**:
  - 단일 모듈+ArchUnit — 셋업은 빠르나 위반이 테스트 실패(사후)로만 잡힘
  - MSA — 공고가 요구하지 않고, 1인 5일 개발에서 운영 비용이 편익을 압도
- **트레이드오프**: 초기 Gradle 설정 비용 (D1 반나절 이내로 제한)

## 결정 5. 프론트: React 19 + TypeScript + Vite, 스트리밍은 SSE

- **상황**: 공고가 React·TypeScript 명시. 후보: Vite SPA / Next.js
- **결정**: Vite SPA + SSE(fetch 스트림) + Vercel AI SDK UI 훅 차용
- **이유**: 사내 시스템은 SEO·SSR 불필요. 백엔드가 Spring인 이상 Next 서버층은 중복.
  UiJin이 tripbook에서 이미 숙련된 스택이라 5일 일정에 유리
- **버린 대안**: Next.js — App Router 학습·배포 복잡도 대비 사내 시스템에서 얻는 것 없음
- **트레이드오프**: 없음에 가까움 (사내 시스템 전제에서)

## 결정 6. LLM: OpenAI API (인터페이스로 격리)

- **상황**: 후보: OpenAI / Anthropic Claude / 로컬 LLM
- **결정**: OpenAI(gpt-4o-mini 계열)로 시작, `LlmClient` 인터페이스로 격리해 교체 가능하게
- **이유**: 기존 키 재사용(비용·발급 절차 0), gpt-4o-mini의 도구 호출 품질이 Text-to-SQL에 충분,
  질의당 비용 목표($0.02)에 부합. 공고는 특정 프로바이더를 요구하지 않음
- **버린 대안**:
  - Claude — 품질 우수하나 신규 키 발급 필요. 격리 구조 덕에 뒤에 어댑터로 추가 가능
  - 로컬 LLM — 도구 호출 신뢰도가 골든셋 목표(85%)를 위협, 데모 환경 재현 부담
- **트레이드오프**: 프로바이더 단일 의존 — 타임아웃·재시도·비용 상한을 전역 정책으로 방어
