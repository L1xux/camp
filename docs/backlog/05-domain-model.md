# [D1] 도메인 모델 — 캠페인 상태머신, 결재 규칙, 예산 불변식

라벨: `D1`, `mvp` / 마일스톤: D1 / 선행: 01 (빌드 골격)

## 배경 / 해결하려는 문제

이 시스템의 존재 이유는 "지금은 엑셀과 수기 결재로 흩어져 있어 강제되지 않는 규칙
(브랜드 권한, 결재 이력, 예산 통제)을 시스템이 강제한다"는 것이다. 그 규칙 자체를
프레임워크 의존 없는 순수 Java로 구현한다. 웹, MCP, 배치 어느 경로로 들어와도
같은 규칙을 통과하고, 프레임워크 없이 테스트되므로 가장 빠르고 두터운 테스트가 가능하다.

## 요구사항

**캠페인 상태머신**
- 상태 5개와 허용 전이. 상태는 sealed interface로 정의해 switch에서 케이스 누락 시
  컴파일 에러가 나게 한다 (새 상태 추가 시 처리 지점 전체가 컴파일러에 의해 드러남):

| 현재 상태 | 전이 가능 | 전이 조건 |
|---|---|---|
| PLANNING(기획) | RECRUITING | 예산과 기간이 설정됨 |
| RECRUITING(섭외중) | IN_EXECUTION | 유효(ACTIVE) 계약 1건 이상 |
| IN_EXECUTION(집행중) | CLOSED | 종료일 도래 또는 수동 종료 |
| CLOSED(종료) | SETTLED | 성과 집계 확정 |
| SETTLED(결산완료) | (없음) | 최종 상태 |

- 역방향 전이와 단계 건너뛰기는 전부 불허. 불법 전이 시도는 도메인 예외로 거부하고,
  예외 메시지에 현재 상태와 시도한 전이를 포함한다

**결재 규칙**
- 계약 금액 구간에 따라 결재선(순차 승인 단계 목록)이 자동 결정된다.
  구간표는 정책 객체로 분리해 표만 바꾸면 되는 구조로:

| 계약 금액(KRW) | 결재선 |
|---|---|
| 5,000,000 미만 | 팀장 |
| 5,000,000 이상 | 팀장 → 본부장 |

- 결재는 순차 진행: 선행 단계가 승인되기 전에는 후행 단계를 처리할 수 없다
- 승인 / 반려: 반려에는 사유가 필수. 반려되면 계약은 REJECTED
- 재상신: REJECTED 계약만 가능, 금액 수정 허용, 결재선은 새로 생성해 처음부터 진행,
  이전 결재 이력은 감사 추적을 위해 보존 (삭제, 덮어쓰기 금지)
- 모든 단계 승인 완료 시점에 계약이 ACTIVE로 전이

**예산 불변식**
- 검증식: `캠페인 예산 ≥ ACTIVE 계약 금액 합계 + 결재 진행 중(PENDING_APPROVAL) 계약 금액 합계`
- 진행 중 금액을 포함하는 이유: 결재 대기 중인 계약도 승인되면 예산을 소비하므로,
  상신 시점에 미리 잡아두지 않으면 대기 중인 두 건이 모두 승인되어 예산을 초과할 수 있다
  (예산 예약 방식. 동시 요청의 경쟁 조건 제어는 API 계층 이슈 08에서 잠금으로 처리하고,
  여기서는 검증식 자체만 책임진다)
- 반려, 재상신 시 예약분 해제/재예약이 정확히 계산되어야 한다

**값 객체와 식별자**
- `Money`: record, KRW 단일 통화, 음수 금지, 0원 계약 금지, 더하기/비교 연산 제공
- 식별자는 전용 타입 (`CampaignId`, `ContractId` 등) — 원시 타입 Long을 도메인 API에
  직접 노출하지 않는다 (ID 뒤바뀜 실수를 컴파일 타임에 차단)
- domain 모듈은 JDK 외 의존성 0 (01번의 ArchUnit 규칙이 강제)

## 예외 케이스

- [ ] 불법 상태 전이 전 조합 → 도메인 예외, 메시지에 현재/시도 상태 포함
- [ ] 예산 초과 상신 → 거부, 예외에 잔여 예산 포함
- [ ] REJECTED가 아닌 계약의 재상신 → 거부
- [ ] 선행 단계 미승인 상태에서 후행 단계 처리 → 거부
- [ ] 이미 승인된 단계의 재처리 → 거부 (중복 처리 방지)
- [ ] 반려 사유 누락 → 거부
- [ ] 경계값: 금액이 정확히 5,000,000 → 2단계 결재선
- [ ] 경계값: 계약 합계가 예산과 정확히 같음 → 허용 (초과만 거부)
- [ ] 음수 금액, 0원 Money 생성 → 생성 시점 거부

## 테스트 케이스 (domain 모듈 단위 테스트 — 프레임워크 없이 실행)

**상태머신 (전이 전수 검증)**
- [ ] 허용 전이 4건 각각 성공 (조건 충족 상태에서)
- [ ] 불허 전이 전 조합(5개 상태 × 5개 목표 − 허용 4건 − 자기 자신 5건 = 16건) 각각 예외
- [ ] RECRUITING → IN_EXECUTION을 유효 계약 0건 상태에서 → 조건 위반 예외
- [ ] PLANNING → RECRUITING을 예산 미설정 상태에서 → 조건 위반 예외
- [ ] SETTLED에서 모든 전이 시도 → 예외

**결재 규칙**
- [ ] 금액 4,999,999 → 결재선 [팀장]
- [ ] 금액 5,000,000 → 결재선 [팀장, 본부장]
- [ ] 1단계 승인 → 2단계 승인 → 계약 ACTIVE
- [ ] 1단계 승인 전 2단계 처리 시도 → 예외
- [ ] 1단계 반려(사유 포함) → 계약 REJECTED, 2단계는 처리 불가
- [ ] 반려 사유 null/빈 문자열 → 예외
- [ ] REJECTED 재상신 → 새 결재선 생성, 기존 이력 보존 확인 (이력 건수 증가)
- [ ] ACTIVE 계약 재상신 시도 → 예외
- [ ] 같은 단계 승인 2회 → 두 번째 예외

**예산 불변식**
- [ ] 예산 1,000만, ACTIVE 600만 → 신규 400만 상신 허용, 400만 초과 상신 거부
- [ ] 예산 1,000만, PENDING 600만 → 신규 500만 상신 거부 (예약분 포함 계산)
- [ ] PENDING 600만이 반려됨 → 신규 800만 상신 허용 (예약 해제 확인)
- [ ] 재상신으로 금액 400만 → 600만 변경 → 예약분이 새 금액으로 재계산
- [ ] 예산과 합계가 정확히 동일 → 허용

**값 객체**
- [ ] Money 음수/0원 생성 → 예외
- [ ] Money 덧셈, 비교 연산 정확성
- [ ] 다른 타입 ID 간 비교가 컴파일되지 않음 (타입 안전성 — 컴파일 테스트)
