# [D2] 캠페인 — CRUD, 상태 전이 API, 후보 관리, 브랜드 데이터 격리

라벨: `D2`, `mvp` / 마일스톤: D2 / 선행: 05 (도메인 모델), 06 (인플루언서 풀)

## 배경 / 해결하려는 문제

마케터가 캠페인을 만들어 인플루언서 후보를 담는 흐름의 API 계층이다.
이 이슈의 가장 중요한 산출물은 **브랜드 데이터 격리(multi-tenancy 격리)의 단일 구현**이다:
"사용자는 자기 브랜드의 데이터만 접근한다"는 규칙을 유스케이스 계층의 한 컴포넌트로
구현하고, 이후 AI 도구 계층(이슈 13)이 같은 컴포넌트를 재사용한다. 같은 규칙이
두 곳에 중복 구현되면 반드시 어긋나고, 어긋난 쪽이 보안 구멍이 된다.

## 요구사항

**캠페인 CRUD**
- `POST /api/campaigns` — 브랜드 ID, 시즌(형식 `YYYY-SS|FW`, 예: `2027-SS`),
  이름(1~100자), 예산(양수 KRW), 기간(시작일 < 종료일)
- `PUT /api/campaigns/{id}` — PLANNING 상태에서만 전체 수정 가능.
  RECRUITING 이후에는 예산 증액과 종료일 연장만 허용, 예산 감액은
  `ACTIVE + PENDING_APPROVAL 계약 합계` 아래로 내릴 수 없다
- `GET /api/campaigns?status=&season=&page=&size=` — 자기 브랜드 것만, 페이징
- `GET /api/campaigns/{id}` — 상세 (후보 목록, 예산 사용 현황 포함)

**상태 전이 API**
- `POST /api/campaigns/{id}/transitions` body `{"target": "RECRUITING"}`
- 전이 로직은 도메인 상태머신(이슈 05)에 위임 — 컨트롤러/서비스에 전이 조건 분기 금지
- 불법 전이 → 400, 도메인 예외 메시지(현재 상태, 시도한 전이) 그대로 응답

**후보 관리**
- `POST /api/campaigns/{id}/candidates` body `{"influencerId": N}` — RECRUITING 상태에서만
- `POST /api/campaigns/{id}/candidates/{candidateId}/confirm` — 확정.
  확정된 후보만 계약 상신(이슈 08) 가능
- `DELETE /api/campaigns/{id}/candidates/{candidateId}` — 계약이 없는 후보만 제거 가능

**브랜드 데이터 격리 (이 이슈의 핵심)**
- 사용자에게 소속 브랜드가 있고, 캠페인 관련 모든 조회/변경은 소속 브랜드 검증을 통과해야 한다
- 구현: 유스케이스 진입 지점의 단일 인가(authorization) 컴포넌트 —
  컨트롤러마다 if문을 두는 방식 금지 (누락 지점이 곧 취약점이 되므로)
- 타 브랜드 리소스 접근은 **404로 응답** (403이 아니라 404: 리소스의 존재 여부 자체를
  숨겨 브랜드 간 정보 유출을 차단한다. 이 선택은 등록 시 재검토 가능)
- 목록 조회는 WHERE 조건으로 자기 브랜드만 — 애플리케이션에서 걸러내는 방식 금지
  (페이징 수치가 깨지고, 누락 시 전체 노출 사고가 된다)

## 예외 케이스

- [ ] 타 브랜드 캠페인: 조회 404, 수정 404, 전이 404, 후보 조작 404 (4경로 전부)
- [ ] 시즌 형식 위반(`2027-XX`), 기간 역전, 예산 0원 이하 → 400
- [ ] RECRUITING 이후 예산 감액이 계약 합계 미만 → 409, 응답에 최소 허용 예산
- [ ] PLANNING 상태에서 후보 담기 → 409 (RECRUITING에서만 가능)
- [ ] 같은 인플루언서 중복 후보 등록 → 409
- [ ] 비활성 인플루언서 후보 등록 → 409 (이슈 06의 비활성 규칙)
- [ ] 존재하지 않는 인플루언서 후보 등록 → 404
- [ ] 계약이 걸린 후보 제거 → 409
- [ ] 유효 계약 0건 상태에서 IN_EXECUTION 전이 → 400 (도메인 조건 위반)
- [ ] 미인증 요청 → 401

## 테스트 케이스

**단위**
- [ ] 시즌 형식 검증: `2027-SS`, `2026-FW` 통과 / `2027-XX`, `27-SS`, 공백 거부
- [ ] 요청 DTO 필드 검증 전 항목 (이름 길이, 예산 부호, 날짜 순서)
- [ ] 인가 컴포넌트 단독: 소속 브랜드 일치 → 통과, 불일치 → 격리 예외

**통합 (실제 Oracle)**
- [ ] 생성 → 조회 왕복, 예산 사용 현황 초기값 0
- [ ] 전체 수명주기: PLANNING → RECRUITING → 후보 → 확정 → (계약은 이슈 08) →
      IN_EXECUTION → CLOSED → SETTLED 순차 전이 성공
- [ ] 불법 전이 3종 이상 (PLANNING→IN_EXECUTION, CLOSED→RECRUITING, SETTLED→CLOSED) → 400
- [ ] 브랜드 격리: 브랜드 A 토큰으로 브랜드 B 캠페인의 조회/수정/전이/후보 각각 → 404
- [ ] 브랜드 격리: 목록 조회에 타 브랜드 캠페인 미포함 + 페이징 총계도 자기 브랜드 기준
- [ ] 후보 중복, 비활성 인플루언서, 계약 있는 후보 제거 → 각각 409
- [ ] 예산 감액 경계: 계약 합계와 동일 금액까지 허용, 1원 미만 거부
- [ ] 상태 필터, 시즌 필터, 페이징 조합 검색

**인가 회귀 방지**
- [ ] 새 캠페인 API가 인가 컴포넌트를 경유하지 않으면 실패하는 테스트
      (엔드포인트 목록 대비 인가 적용 목록 대조 또는 ArchUnit 규칙)

## 완료 조건

- [ ] 브랜드 격리가 단일 컴포넌트로 존재하고, 모든 캠페인 엔드포인트가 경유함을 테스트로 증명
- [ ] 캠페인 생성부터 후보 확정까지 API 호출 순서로 재현 가능
- [ ] 예외 케이스 전부에 대응 테스트 존재
