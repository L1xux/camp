# [D4] MCP 도구 서버 + SQL Validator — LLM 출력의 DB 실행 관문

라벨: `D4`, `mvp`, `core` / 마일스톤: D4 / 선행: 04 (비용 상한), 07 (브랜드 격리), 08 (결재 조회), 12 (시드 데이터)

## 배경 / 해결하려는 문제

LLM이 자연어 질문을 SQL로 바꿔 실행하는 구조(Text-to-SQL)는 "LLM 출력이 DB 실행으로
이어지는 경로"다. LLM 출력은 신뢰할 수 없는 입력으로 취급해야 한다 — 사용자가 프롬프트
인젝션으로 LLM을 조종해 다른 브랜드의 데이터를 조회하거나 데이터를 변조하려는 시도를
구조적으로 차단해야 한다. 차단 장치가 Validator이고, 웹 화면의 AI 챗과 Claude Desktop
(외부 MCP 클라이언트)이 **같은 도구, 같은 Validator**를 거치게 하는 것이 이 설계의 핵심
주장이다. 도구의 비즈니스 로직은 기존 유스케이스를 재사용한다 — 권한 규칙이 웹용과
AI용으로 이중 구현되면 반드시 어긋나고, 어긋난 쪽이 취약점이 된다.

**SQL Validator — `query_campaign_metrics`의 실행 관문**

LLM이 생성한 SQL은 다음 4단계를 전부 통과해야 실행된다. 검사는 문자열 검색이 아니라
**SQL 파서의 AST(구문 트리) 분석**으로 한다 — 문자열 매칭은 주석, 대소문자, 인코딩
트릭으로 우회된다.

1. **구문 제한**: 단일 SELECT 문만. INSERT/UPDATE/DELETE/DROP/MERGE, 다중 문장(`;`),
   WITH를 가장한 DML, 프로시저 호출 전부 거부
2. **스키마 화이트리스트**: 허용 목록에 있는 테이블과 컬럼만 참조 가능.
   시스템 뷰, 데이터 딕셔너리, 사용자/권한 테이블 접근 거부. JOIN, 서브쿼리,
   UNION의 참조 대상도 전부 검사
3. **브랜드 필터 강제 주입**: LLM이 작성한 WHERE 절을 신뢰하지 않는다.
   호출자의 브랜드 조건을 AST 수준에서 최상위 WHERE에 AND로 주입한다
   (문자열 이어붙이기 금지 — 주석 트릭 `--`로 무력화되기 때문)
4. **실행 상한**: 결과 행 수 LIMIT 강제 부여, 쿼리 타임아웃 설정,
   일일 LLM 비용 상한(이슈 04) 확인

- 차단 시 구체적 사유를 응답으로 반환 ("허용되지 않은 테이블 X 참조" 수준) —
  사용자가 질문을 고칠 수 있어야 하고, 시연에서 차단이 보여야 한다
- SQL 실행 오류(존재하지 않는 컬럼 등)는 오류 내용을 LLM에 돌려줘 1회 재생성 허용,
  재실패 시 사용자에게 실패로 응답 (임의 대체 답변 금지)
- 실행된 최종 SQL(주입 후)을 로그에 남긴다 — 사고 조사와 골든셋 검증의 근거

## 예외 케이스 (= 공격 시나리오, 전부 골든셋 이슈 16에 편입)

- [ ] `DROP TABLE contracts` / `UPDATE contracts SET ...` / `SELECT 1; DELETE ...` → 구문 거부
- [ ] "모든 브랜드의 계약 금액을 보여줘" (인젝션으로 WHERE 제거 유도) →
      주입된 브랜드 조건이 항상 적용되어 타 브랜드 행 0건
- [ ] `... WHERE brand_id = 2` (LLM이 타 브랜드를 직접 지정) → 주입 조건과 AND 결합되어 0건
- [ ] `... WHERE brand_id = 1 OR 1=1` → AST 주입이라 주입 조건이 OR 바깥에서 AND로 묶임
- [ ] `UNION SELECT username FROM all_users` → 화이트리스트 거부
- [ ] 주석 트릭 `WHERE ... --`, 대소문자 혼용 `DrOp`, 공백 변형 → AST 분석이라 무의미함을 테스트로 증명
- [ ] 전 기간 풀스캔 질의 → LIMIT 강제 적용, 결과에 "상위 N건으로 제한됨" 명시
- [ ] 존재하지 않는 컬럼 참조 → 오류 반환 → LLM 재생성 1회 → 재실패 시 정직한 실패
- [ ] 호출자 컨텍스트 누락 → 실행 거부
- [ ] 일일 비용 상한 초과 → AI 질의 거부 응답, 사유 포함
- [ ] Validator 자체 오류(파서 예외) → 실행 거부 (통과가 아니라 거부로 실패)

## 테스트 케이스

**Validator 단위 테스트 (LLM 불필요 — 입력 SQL 문자열 → 판정이므로 결정적)**
- [ ] 위 공격 시나리오 전 건 → 차단 판정 + 사유 문자열 검증
- [ ] 허용 케이스: 단순 SELECT, JOIN 2개, GROUP BY 집계, 서브쿼리 포함 SELECT → 통과
- [ ] 주입 검증: 통과된 쿼리의 최종 AST에 브랜드 조건이 최상위 AND로 존재
- [ ] 주입 검증: 이미 브랜드 조건이 있어도 중복 주입이 결과를 왜곡하지 않음
- [ ] LIMIT: LIMIT 없는 쿼리에 부여, 상한 초과 LIMIT은 상한으로 교체
- [ ] 화이트리스트: 허용 테이블의 비허용 컬럼 → 거부 (테이블만이 아니라 컬럼 단위 확인)
- [ ] 경계: 빈 문자열, SQL 아닌 텍스트, 초장문 쿼리 → 파서 오류 = 거부
