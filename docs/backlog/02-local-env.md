# [D1] 로컬 실행 환경 — docker-compose(Oracle 23ai), DB 마이그레이션 체계

라벨: `D1`, `setup` / 마일스톤: D1 / 선행: 01 (빌드 골격)

## 배경 / 해결하려는 문제

통합 테스트는 인메모리 DB가 아니라 운영과 같은 Oracle 위에서 돌아야 의미가 있다
(Oracle 전용 기능인 파티셔닝, 벡터 검색을 쓰는 프로젝트라 H2 대체가 불가능하다).
또한 DB 스키마 변경이 마이그레이션 파일로만 이루어지는 체계를 첫 테이블 생성 전에
갖춰야 한다 — 도입이 늦으면 손으로 만든 스키마가 이력 밖에 남아 환경 간 불일치의
원인이 된다.

## 요구사항

**docker-compose**
- Oracle Database Free 23ai 컨테이너
- 포트 매핑 `127.0.0.1:1522:1521` — 호스트 바인딩 주소를 명시한다
  (1521은 다른 프로젝트 점유 가능, 와일드카드 바인딩은 이 PC의 장애 이력상 금지)
- 헬스체크: DB가 실제 접속을 받을 때까지 대기 (컨테이너 running ≠ DB ready)
- 볼륨 정책: dev는 데이터 소실 허용, 시드 스크립트 재실행으로 복구 — README에 명시

**계정과 권한**
- 앱 전용 계정 생성 스크립트 (최소 권한: 자기 스키마의 DML/DDL만)
- SYSTEM/SYS로 애플리케이션 접속 금지

**DB 마이그레이션 (Flyway 또는 Liquibase — 선정 근거를 ADR-003으로 기록)**
- 모든 스키마 변경은 버전 붙은 마이그레이션 파일로만, 수동 ALTER 금지
- 적용된 마이그레이션 파일은 불변 — 수정이 필요하면 새 버전 파일 추가
- 롤백 스크립트(undo) 작성 규칙 확립: 파괴적 변경(컬럼 삭제 등)은 롤백 불가능성을
  마이그레이션 파일 주석에 명시
- V001 베이스라인 마이그레이션으로 파이프라인 검증

**설정 관리**
- `.env.example` 커밋 (DB 접속 정보, 이후 API 키 자리), 실제 `.env`는 `.gitignore`
- 애플리케이션 설정에서 시크릿은 전부 환경변수 참조 — 하드코딩 금지

## 예외 케이스

- [ ] 컨테이너 기동 실패 (메모리 부족, 포트 충돌) → 로그와 함께 원인, 조치를
      `docs/ENVIRONMENT.md`에 기록
- [ ] 마이그레이션 도중 실패 → 실패 지점 이전까지만 적용된 상태를 확인하고,
      수동 개입 절차(repair)를 RUNBOOK에 기록
- [ ] 적용 완료된 마이그레이션 파일이 변경됨 (체크섬 불일치) → 기동 거부가 정상 동작
- [ ] 컨테이너 재시작 후 앱 재접속 → 커넥션 풀이 자동 복구 (재기동 불필요)
- [ ] 앱 계정으로 타 스키마 접근 → 권한 오류

## 테스트 케이스

**환경 기동**
- [ ] `docker compose up -d` → 헬스체크 통과 → 앱 계정 JDBC 접속 성공
- [ ] 헬스체크 통과 전 접속 시도 → 실패 (대기 로직 검증)
- [ ] 컨테이너 중지 후 재시작 → 별도 조치 없이 앱 커넥션 회복

**마이그레이션**
- [ ] V001 적용 → 이력 테이블에 버전, 체크섬, 적용 시각 기록
- [ ] 같은 버전 재실행 → no-op (멱등)
- [ ] 적용된 파일 내용 변경 후 기동 → 체크섬 검증 실패로 거부
- [ ] 새 버전 추가 후 기동 → 해당 버전만 추가 적용
- [ ] 잘못된 SQL이 든 마이그레이션 → 실패 시 이력 테이블 상태 확인 (부분 적용 여부 문서화)

**권한**
- [ ] 앱 계정으로 자기 스키마 테이블 생성/조회 성공
- [ ] 앱 계정으로 SYSTEM 스키마 조회 → 거부
- [ ] gitleaks 실행 → 레포에 접속 정보 미검출

## 완료 조건

- [ ] `docker compose up -d` 한 번으로 로컬 DB 재현
- [ ] 마이그레이션 도구 선정과 규칙이 ADR-003으로 기록됨
- [ ] 이후 모든 스키마 변경이 마이그레이션 파일을 거치는 상태
