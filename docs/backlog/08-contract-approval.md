# [D2] 계약과 결재 워크플로우 — 결재선 자동 생성, 승인/반려/재상신, 예산 동시성 제어

라벨: `D2`, `mvp` / 마일스톤: D2 / 선행: 05 (도메인 모델), 07 (캠페인)

## 배경 / 해결하려는 문제

계약 상신부터 결재 완료까지의 워크플로우 API다. 돈이 걸린 경로라 두 가지가 핵심이다.

1. **트랜잭션 원자성**: 최종 승인 시점에 "계약 유효화(ACTIVE 전이)"와 "예산 소비 확정"이
   하나의 트랜잭션이어야 한다. 하나만 반영되면 예산 장부와 계약 상태가 어긋난다.
2. **경쟁 조건(race condition) 제어**: 같은 캠페인에 두 건의 계약이 거의 동시에 상신될 때,
   각각은 잔여 예산 이내지만 둘 다 통과하면 합계가 예산을 초과하는 문제.
   예산 검증과 예약이 직렬화되지 않으면 발생한다 (lost update 유형).

## 요구사항

**계약 상신**
- `POST /api/contracts` body `{campaignId, influencerId, amount}` →
  `201 {contractId, status: "PENDING_APPROVAL", approvalLine: [{step, role, status}]}`
- 전제 조건: 캠페인이 RECRUITING 이상, 해당 인플루언서가 **확정된 후보**
- 상신 시점 처리(한 트랜잭션): 예산 검증(도메인 불변식 — ACTIVE + PENDING 합계 + 신규 금액
  ≤ 예산) → 결재선 자동 생성(도메인 규칙의 금액 구간표) → PENDING_APPROVAL 저장

**예산 동시성 제어**
- 예산 검증~예약 구간을 직렬화한다. 방식은 캠페인 행 비관적 잠금
  (`SELECT ... FOR UPDATE`) 또는 낙관적 잠금(`@Version` + 재시도) 중 택일 —
  선택과 근거(경합 빈도 예상, 데드락 위험)를 PR에 기록
- 동시 상신 중 늦은 쪽은 예산 부족이면 409로 거부되어야 하며, 절대 둘 다 통과하면 안 된다

**결재 처리**
- `POST /api/contracts/{id}/approvals` body `{"decision": "APPROVE"|"REJECT", "comment": "..."}`
- 처리 자격: 현재 차례 단계의 역할(팀장 또는 본부장) + 캠페인과 같은 브랜드 소속
- REJECT는 comment 필수 → 계약 REJECTED, 예산 예약 해제
- 중복 처리 방지: 이미 처리된 단계에 재요청(더블클릭, 네트워크 재전송) → 409,
  상태 변화 없음 (멱등하지 않은 연산이므로 명시적 거부를 택한다)
- **최종 승인 트랜잭션**: 마지막 단계 승인 = 계약 ACTIVE 전이 + 예산 소비 확정.
  도중 예외 시 전체 롤백 (계약은 PENDING_APPROVAL 유지)

**재상신**
- `POST /api/contracts/{id}/resubmit` body `{amount}` — REJECTED 계약만,
  금액 변경 가능(재상신 시점에 예산 재검증), 새 결재선으로 처음부터
- 이전 결재 이력은 보존 — 감사 추적용

**조회**
- `GET /api/approvals/pending` — 내 역할이 현재 차례인 결재 대기 목록 (내 브랜드만).
  이 유스케이스는 이후 AI 도구 `list_pending_approvals`(이슈 13)가 그대로 재사용한다
- `GET /api/contracts/{id}` — 상세 + 결재 이력 전체 (처리자, 시각, 결정, 사유)

## 예외 케이스

- [ ] 미확정 후보로 상신 → 409
- [ ] PLANNING 상태 캠페인에 상신 → 409
- [ ] 예산 초과 상신 → 409, 응답에 잔여 예산
- [ ] 동시 상신 경쟁: 잔여 800만에 500만 2건 동시 → 정확히 1건 성공, 1건 409
- [ ] 결재 자격 위반: 마케터의 승인 시도, 팀장 차례에 본부장 처리, 타 브랜드 결재자 → 403 또는 404
- [ ] 반려 사유 누락 → 400
- [ ] 이미 처리된 단계 재요청 → 409, 이력에 중복 기록 없음
- [ ] REJECTED 아닌 계약 재상신 → 409
- [ ] 캠페인이 CLOSED 이후인데 재상신 → 409
- [ ] 최종 승인 트랜잭션 중 예산 갱신 실패(예외 주입) → 계약 상태 롤백 확인
- [ ] 존재하지 않는 계약 ID → 404

## 테스트 케이스

**단위 (유스케이스 계층, 도메인은 이슈 05에서 검증됨)**
- [ ] 상신 전제 조건 4종 (캠페인 상태, 후보 확정 여부, 예산, 브랜드) 각각의 거부
- [ ] 결재 자격 판정: 역할 × 차례 × 브랜드 조합 8케이스 표로 검증
- [ ] 재상신 금액 변경 시 예산 재검증 호출 확인

**통합 (실제 Oracle, 트랜잭션 검증 포함)**
- [ ] 정상 흐름: 490만 상신 → 팀장 승인 → ACTIVE / 500만 상신 → 팀장 → 본부장 → ACTIVE
- [ ] 반려 흐름: 반려(사유) → REJECTED → 예산 예약 해제 확인(신규 상신 가능 금액 증가)
- [ ] 재상신 흐름: 금액 수정 재상신 → 새 결재선, 이력 조회에 반려 기록 잔존
- [ ] 최종 승인 원자성: 승인 처리 중 예외 주입 → 계약 PENDING 유지 + 예산 무변화
      (둘 다 검증)
- [ ] 결재 이력: 각 처리의 처리자, 시각, 사유가 조회 API에 노출

**동시성 (스레드 풀로 병렬 요청)**
- [ ] 동시 상신 2건 (합계 초과) → 1건 성공 1건 409, DB의 예약 합계가 예산 이내
- [ ] 동시 상신 10건 (전부 통과하면 초과) → 통과 건수 합계가 예산 이내
- [ ] 같은 결재 단계 동시 승인 2건 → 1건 성공 1건 409, 이력 1건만 기록
- [ ] 승인과 반려 동시 요청 → 하나만 반영, 최종 상태가 반영된 쪽과 일치
